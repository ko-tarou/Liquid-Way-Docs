# ADR-0004: オフラインデータ同期と競合解決

- Status: Proposed
- Date: 2026-05-17
- Deciders: ko-tarou, Mako（参加意思確認中）

---

## Context

LiqMesh は通信断絶中に各端末／昇格サーバー内へ時系列ログとして蓄積し、メッシュ再結合や上位接続復活時に差分を統合する（議事録 §9.7、liqmesh.md §5「オフライン蓄積 / 自動同期」）。ADR-0003 が split-brain（分断中の独立 Leader）を許容するため、**再結合時に履歴を失わない競合解決モデル**が必須です。扱うデータ種別は以下。

| 種別 | 性質 | 競合の起き方 |
|---|---|---|
| D1 被害報告 | ほぼ append（新規投稿） | 重複（同一事象を別端末が別々に報告） |
| D2 写真 | 不変 blob + メタ | 同一現場の写真が別 ID で重複 |
| D3 ステータス更新 | 同一エンティティを複数端末が更新 | Last-writer 競合（避難所Aの給水「充足/不足」が割れる） |

加えて、AI（ADR-0006 のサーバー側 LFM）が機能 6.2「重複統合・矛盾解消」を担う。**どこまでをアルゴリズム的整合で、どこからを AI 統合で**やるかの責務分離も本 ADR で定義します。

---

## Decision

**データ種別ごとに CRDT 型を使い分ける。LWW 単独・ベクタークロック単独は採らない。**

| 種別 | 採用 CRDT | 理由 |
|---|---|---|
| D1 被害報告 | **OR-Set（Observed-Remove Set）** の add 専用運用（実質 Grow-only Set + tombstone は撤回専用） | 報告は基本 append。誤報撤回のみ remove。並行 add が衝突せず全件保持＝再結合で報告を失わない |
| D2 写真 | **イミュータブル + content-addressed ID（ハッシュ）**。集合は OR-Set | 同一バイト列は同一 ID に収束。別 ID の「視覚的重複」はアルゴリズムでは消さず AI に委ねる |
| D3 ステータス | **フィールド種別で二分**: (a) 生命安全フィールド（給水/医療/危険度等）は **danger-wins merge または両値併記**、(b) 安全に無関係なフィールドのみ **LWW-Element-Set**（要素ごと最終書込み勝ち、タイブレークに端末 ID） | 素の LWW は「給水不足 → 充足」を時計勝者だけで安全でない側へ決定的に消しうる。生命安全に関わる項目では不可 |

タイムスタンプは端末物理時計が信用できないため **Hybrid Logical Clock（HLC）** を全レコードに付与し、LWW のタイブレークと因果順序付けに使う（純粋ベクタークロックは端末数増でメタデータが線形膨張するため不採用、HLC は定数サイズ）。

#### D3 の安全側マージ規則（ADR-0005 の安全側原則と整合）

- **生命安全フィールド（給水/医療/危険度/救助要否 等）**: 素の LWW を**禁止**する。並行更新は **より危険側を保持する merge（danger-wins）**（例: 「不足」と「充足」が並行したら「不足」を保持）か、解消不能なら**両値併記**（報告A/報告B）として AI（ADR-0006 機能 6.2）または人間の再解決へ回す。「データを失う方向の判断は決定的層が行う」本 ADR の責務原則に従い、安全でない側への決定的な消去を構造的に防ぐ。
- **安全に無関係なフィールド**（表示順の好み・任意ラベル等）: 従来どおり LWW-Element-Set で単一現在値に収束させる。
- これは ADR-0005「AI スコア未付与時は安全側に倒す」と同一の安全哲学であり、両 ADR で相互参照する（ADR-0005 §AI スコア未付与）。

### アルゴリズム的整合 vs AI 統合の責務分離

| 層 | 担当 | 何をするか |
|---|---|---|
| **アルゴリズム層（決定的）** | CRDT マージ | 完全同一レコードの収束、撤回反映、ステータスの LWW 解決、content-hash による完全一致写真の de-dup。**ここは AI を使わない**（決定性 & 制御性、liqmesh.md §9） |
| **AI 層（ADR-0006, server-only）** | LFM 機能 6.2 | 「水が足りない」×30 件のような**意味的重複の統合**、矛盾の併記（報告A/報告B）、視覚的に同一現場の写真群のクラスタリング（機能 6.5 と連携） |

境界の原則: **データを失う方向の判断は必ずアルゴリズム層が決定的に行い、AI は「表示用の統合ビュー生成」に限定**する。AI 出力は元レコードを破壊せず派生ビューとして保持する（誤統合のロールバック可能性を担保）。

### OR-Set tombstone の GC（時間境界ヒューリスティック）

OR-Set の tombstone（撤回マーカ）を放置すると単調増加するため、GC を**決定として**定める（従来の「要検証」止まりを格上げ）。

- **規則**: 撤回（tombstone 化）後 **N 時間**（既定値は推測。`N = 24h` を初期値とし、実機・実セッション長で要調整と明記）経過した tombstone を物理削除する。
- **因果安定を待たない理由**: LiqMesh は開放メンバーシップ（誰でも参加/離脱）かつ分断常態のメッシュであり、全レプリカの causal stability（その撤回を全ノードが観測済み）の成立保証がない。因果安定を待つ古典的 GC はこの環境では収束しないため、**時間境界ヒューリスティック**を採る。
- **受容するトレードオフ**: ごく稀に、N 時間より長く分断していたノードが古い add を持って再結合すると、削除済み要素が**復活（resurrection）**しうる。これを**受容しログに残す**（監査可能にし、AI/人間が異常として検知できるようにする）。安全側に倒すべき撤回（誤報の撤回）であっても resurrection の可能性は残るため、生命安全に関わる撤回は併記扱い（上記 D3）にフォールバックして人手確認へ回す。

## Alternatives Considered

| 案 | 長所 | 短所 | Android 制約 | 却下理由 |
|---|---|---|---|---|
| **種別別 CRDT（OR-Set/LWW-Element-Set）+ HLC（採用）** | 再結合で報告を失わない。種別に最適。メタデータ定数サイズ | 実装が型ごとに分岐。tombstone GC 設計が必要 | Room/SQLite 上に CRDT メタを持つ実装コスト | — |
| Last-Write-Wins 単独（全データ） | 実装最小 | **並行報告が消える**（D1 で致命的）。災害情報の欠落は許容不可 | 端末時計ズレで誤った勝者 | D1 要件（append を失わない）に反する |
| ベクタークロック単独 | 因果関係を厳密追跡 | **端末数に比例してメタデータ膨張**。数十端末メッシュで非現実的。値の自動マージ規則は別途必要 | 帯域・ストレージ圧迫 | スケール（数十端末）でメタデータコスト過大。HLC で因果は十分 |
| AI に競合解決を全面委任 | 実装が単純に見える | 非決定的でロールバック不能。データ消失リスク。liqmesh.md §9「決定性 & 制御性」に反する | サーバー端末の推論負荷増 | データ整合を非決定 AI に委ねるのは設計原則違反 |

## Consequences

### 正の帰結

- ADR-0003 の split-brain 後に**全報告を保持したまま**マージでき、災害情報の欠落を構造的に防ぐ。
- 決定的層と AI 層の責務が明確で、liqmesh.md §9「決定性 & 制御性 ★★★★」の主張を技術的に裏付け。
- HLC により端末時計ズレに依存しない順序付けができる。

### 負の帰結・受容するトレードオフ

- CRDT メタ（HLC、tombstone）の保持と GC 設計が必要で実装コスト増を受容。
- OR-Set tombstone は時間境界 GC（既定 N=24h）で物理削除するが、その代償として**稀な resurrection（削除復活）を受容**する。生命安全に関わる撤回は併記フォールバックで人手確認へ。
- AI 統合ビューは派生のため、元レコードと二重に保持しストレージを消費。
- D3 の生命安全フィールドは LWW 不可で danger-wins/併記となるため、「現在値が常に 1 つ」ではなくなる項目が出る（UI で両値を見せる前提が必要。これを受容）。

### ストレージ逼迫時の写真退避／間引き方針

D2 写真（数百 KB〜数 MB）はストレージを最も圧迫する。昇格サーバー端末のストレージが閾値（要実機調整）を超えた場合の退避規則を定める。

- **原則: 退避＝データ損失なので、何をいつ捨てるかは決定的層（アルゴリズム層）が決める**。AI には委ねない（本 ADR の責務原則と同一）。
- 退避順序（決定的）: (1) AI 派生ビューや再生成可能なサムネイル等の**派生物を先に破棄**、(2) 次に **content-hash 重複が確認済みの冗長写真**を 1 枚残して間引き、(3) それでも不足なら**優先度の低い（ADR-0005 で NORMAL/LOW 相当）かつ最古の写真**から退避。CRITICAL/HIGH に紐づく写真は最後まで保持。
- 退避は隣接 GO への bounded 転送（ADR-0005 §CRITICAL 退避と同じストア&フォワード）を試み、不能なら監査ログ付きで降格保持または物理削除。**元の被害報告メタ（D1）は写真を失っても保持**する（テキストは小さく、情報の骨格を残す）。

### フォローアップ

- ADR-0005: マージ後レコードへの優先度スコア付与順序（AI スコア未付与の扱い）、安全側原則の相互参照。
- ADR-0006: 機能 6.2 の意味的統合をどのモデル／実行方式で回すか。
- 要検証: tombstone GC の N 時間実機調整、HLC スキューの実機計測、Room スキーマへの CRDT メタ実装、ストレージ退避閾値の実機調整。
