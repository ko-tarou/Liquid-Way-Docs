# ADR-0003: 動的サーバー選出アルゴリズム

- Status: Proposed
- Date: 2026-05-17
- Deciders: ko-tarou, Mako（参加意思確認中）

---

## Context

LiqMesh は「安定電源を確保した端末が動的に LFM サーバー役に昇格し、悪化したら次点へ無停止引き継ぎ」する（liqmesh.md §4.2、議事録 §9.2）。不安定な災害下メッシュで、以下を満たす leader election を定義します。

| # | 要件 |
|---|---|
| E1 | 充電中／大容量電池／高スペック端末を優先してサーバー化 |
| E2 | 周期ハートビートで生存監視 |
| E3 | サーバー故障時に次点へフェイルオーバー |
| E4 | メッシュ分断時の split-brain と、再結合時のマージ方針 |
| E5 | ADR-0002 の Wi-Fi Direct GO（Group Owner）に選出結果をマッピングできる |

古典的 leader election（Bully / Raft）は「全ノード均質・到達安定」を暗黙前提にしますが、LiqMesh は**電源状態という外部属性で優先順位が決まる**点と**頻繁な分断**が前提な点が異なります。

---

## Decision

**「重み付きサーバー適性スコア + 周期ハートビート + 分断許容（split-brain を許し再結合時にマージ）」を採用する。** Raft のような厳密な過半数合意は採らない（分断が常態で過半数が成立しないため）。

### スコア式

各端末 i は周期的に自スコア S_i をブロードキャストする（液mesh.md §4.2-1 のブロードキャストに対応）。

```
S_i = w_p · P_i        # 電源: AC給電=1.0, モバイルバッテリ=0.6, バッテリ単独=0.0
    + w_b · B_i        # 電池残量 0.0–1.0 (残量%/100)
    + w_c · C_i        # 計算能力 0.0–1.0 (NPU有=1.0, 高CPU=0.6, 低=0.3)
    + w_s · St_i       # 安定度 0.0–1.0 (直近Tでの離脱回数の逆指標、かつ温度項を内包)
    - w_l · L_i        # 負荷ペナルティ 0.0–1.0 (現在の推論キュー長/上限)
```

初期重み（要実機チューニング、推測値と明記）: `w_p=0.40, w_b=0.20, w_c=0.25, w_s=0.10, w_l=0.05`。電源を最重要に置くのは liqmesh.md §4.2「安定電源を確保した端末」が一次基準だから。同点時は端末 ID 辞書順で決定的にタイブレーク（再現性のため）。

安定度 St_i には**サーマル項**を内包する: SoC 温度が閾値（既定 ≥ サーマルスロットリング開始点、機種依存・要実機計測）に達した端末は St_i を線形に減点し、選出から自然に外れるようにする。さらに、Leader 在任中に温度が危険域（持続スロットリング域）へ入った端末は **温度トリガの自発降格**を行う（下表「自発降格」の温度版）。スマホでの持続推論＋無線送受は発熱で性能劣化・選出フラッピングを招くため、温度を選出と降格の一次シグナルに含める。

### 選出・再選出のトリガ

| トリガ | 条件 | 挙動 |
|---|---|---|
| 初期選出 | グループ形成直後、ハートビート 1 周期収集後 | 最大 S_i の端末を Leader=LFM サーバー、ADR-0002 の Wi-Fi Direct GO に固定 |
| ハートビート喪失 | Leader から 3 周期（既定 3×2s=6s、要調整）応答なし | 残存ノードで次点（2 番目に高い S_i）へフェイルオーバー |
| 自発降格 | Leader の S_i が 2 番手より閾値 Δ=0.15 下回り T_hyst=15s 継続 | ヒステリシス付きで次点へ委譲（フラッピング防止） |
| 過負荷 | L_i が上限到達かつ次点 S が現 Leader を上回る | 委譲（ADR-0005 のキュー溢れと連動） |

ハートビート間隔は既定 2s（推測初期値、災害下の電力と検出遅延のトレードオフで要実測調整）。

### 分断（split-brain）と再結合

- **分断は許容する**: メッシュが A/B に割れたら各部分が独立に Leader を選び、各々ローカルに LFM サーバーを持つ（可用性優先 = AP 型）。これは ADR-0004 の「分断中も append し続ける」整合性モデルと整合。
- **再結合時のマージ**: 二つの Leader が再会したら、(1) スコアの高い方を新 Leader に確定、(2) データは ADR-0004 の CRDT マージで統合（どちらの履歴も失わない）、(3) 旧 Leader はクライアントに降格しキューを新 Leader へ転送。
- **エポック番号**: 各 Leader 任期に単調増加エポックを付与し、再結合時に古いエポック由来の制御メッセージを破棄して指揮系統の混線を防ぐ。

### GO ↔ Leader の束ねとフェイルオーバー手順

ADR-0002 は「GO 選出・再選出は本 ADR で詳細化」と委ねている。LiqMesh の Leader（アプリ層の LFM サーバー）と Wi-Fi Direct GO（OS が握る物理グループの親）は別レイヤで、フェイルオーバーの**時間スケールが一桁以上違う**点を明示する。

- **(a) 遅延差**: アプリ層フェイルオーバーは HB 喪失検知ベースで**既定 6s**（3×2s）で次点 Leader を決められる。一方 OS の Wi-Fi Direct GO 再形成（旧 GO 喪失 → 新グループのネゴ・DHCP 再配布・クライアント再接続）は実測で**秒〜数十秒**かかりうる（端末・OS 依存、要実機計測）。この差を埋めないと「新 Leader は決まったが下層の物理グループがまだ無い」空白が生じる。
- **(b) リレー継続による移譲**: 旧 GO は、自身が Leader 役を失っても、**新 Leader のグループ形成が完了するまでは物理 GO / リレーを継続**する（即座に降りない）。新 Leader が GO 化し DHCP が立ち上がったことを確認してから、旧 GO は物理グループを解放する。これにより (a) の空白中もメッセージ転送が途切れない。
- **(c) エポックによる旧指揮系統の破棄**: 移譲完了後、旧 Leader/GO が遅延して送る制御メッセージは**古いエポック**を持つため受信側で破棄される（上記「エポック番号」と同一機構）。旧 GO 由来のデータメッセージ自体は ADR-0004/0005 の de-dup と CRDT マージで安全に吸収する（捨てない）。
- **(d) 時系列（Leader 喪失 → 旧 GO 暫定継続 → 新 GO ネゴ → キュー移譲 → 旧 GO 降格）**:
  1. 残存ノードが Leader の HB を 3 周期喪失（既定 6s）。
  2. 残存ノードがスコアで次点を新 Leader に確定（新エポック発番）。**この時点では旧 GO が物理リレーを暫定継続**。
  3. 新 Leader が Wi-Fi Direct GO 化をネゴ（OS レイヤ、秒〜数十秒）。
  4. 新 GO の DHCP 稼働を確認後、旧 Leader が保持していた優先度キューを新 Leader へ転送（ADR-0005 のキュー引き継ぎ。CRITICAL から順に移譲）。
  5. キュー移譲完了を確認し、旧 GO が物理グループを解放してクライアントへ降格。以降の旧エポック制御メッセージは (c) で破棄。

### 信頼モデルと受容リスク

- **(a) スコープ外の明言**: 本フェーズ（第 1 弾）では、選出スコア S_i・`origin_id`・HB はすべて**自己申告・無認証**であり、ノード間の暗号認証や制御メッセージ署名は**本フェーズのスコープ外**とする。完全な認証/署名は将来フェーズ（01_vision_and_scope で集約）で扱う。
- **(b) 受容するリスク**: 悪意ノードが (i) 過大な S_i を詐称して不当に Leader を奪取しメッシュの中枢を握る、(ii) `origin_id` を詐称して他端末になりすます、(iii) ADR-0005 の CRITICAL を詐称して優先度キューを占有する（DoS）――これらが本フェーズでは**原理的に可能**であることを受容する。災害下の協調を最優先し、認証コストより可用性を採る判断。
- **(c) 最低限の緩和（認証なしで効く範囲）**:
  - **スコア変化量の妥当性上限**: 1 端末の S_i が短時間に物理的にありえない跳躍（例: 1 周期で 0.0 → 1.0）をした場合、その更新を無視またはランプ制限する（電源・電池は連続変化が物理前提）。
  - **origin 単位のレート制限**: `origin_id` ごとに制御メッセージ・報告の受理レートに上限を設け、単一 origin によるフラッディングを抑制する。
  - **CRITICAL レート上限（#2 / ADR-0005 連動）**: ADR-0005 の CRITICAL 実上限と `origin_id` 単位レート制限を併用し、CRITICAL 詐称による無限キュー占有を構造的に不能にする。
- これらは攻撃を防ぎきるものではなく**被害の上界を与える緩和**である点を明記する（受容リスク）。

## Alternatives Considered

| 案 | 長所 | 短所 | Android 制約 | 却下理由 |
|---|---|---|---|---|
| **重み付きスコア + HB + 分断許容（採用）** | 電源属性を直接反映。分断常態に強い。GO へ素直にマッピング | 厳密合意なし＝一時的多重 Leader を許容（設計上の選択） | バックグラウンド制約下で HB 周期を詰めにくい（doze）。前景サービス前提 | — |
| Bully アルゴリズム | 実装単純、最大 ID が必ず勝つ | ID＝適性ではない（電源無視）。選出時のメッセージ嵐。分断耐性なし | 同上 | E1（電源優先）を表現できない。スコアの方が要件に直結 |
| Raft-lite（過半数合意） | 強い一貫性、Leader 一意保証 | **分断時に過半数が成立せず全停止**しうる。災害下で致命的 | HB を詰めると電力消費大 | E4（分断常態で可用性優先）と根本的に不一致 |
| 固定 Leader（Ryzen AI PC 固定） | 実装ゼロ、デモ安定 | 端末メッシュとして成立しない（LiqMesh の本質を失う） | — | 本番 Vision 不適。ただし 12h MVP のデモ縮退としては併用（議事録 §11） |

## Consequences

### 正の帰結

- 電源・スペックという「サーバーに向くか」の本質属性で選出でき、liqmesh.md §4.2 の意図に忠実。
- 分断を障害でなく通常状態として扱うため、災害下の頻繁な切断で停止しない（可用性優先）。
- ADR-0002 の GO とエポックの対応で、転送層と制御層の責務境界が明確。

### 負の帰結・受容するトレードオフ

- **一時的に複数 Leader が並存**しうる（split-brain 許容の代償）。データ衝突は ADR-0004 の CRDT に委ねる前提で受容。
- スコア重みとハートビート周期は**実機チューニング必須**（現値は推測初期値）。電力と検出遅延はトレードオフ。
- フラッピング対策（ヒステリシス／エポック）を入れる分、制御パスの状態数が増える。
- **スマホでの持続推論＋無線送受は発熱で性能劣化を招き**、サーマル項を入れても高温域での選出フラッピングや実効スループット低下は完全には消せない（受容し、温度トリガ降格と #2 のレート上限で被害を抑える）。
- 無認証選出のため**なりすまし／Leader 奪取／CRITICAL 詐称が原理的に可能**（上記「信頼モデルと受容リスク」で受容。緩和は被害上界のみ）。

### フォローアップ

- ADR-0004: 再結合マージで失わないための CRDT 型定義。
- ADR-0005: Leader 委譲時の優先度キュー引き継ぎ手順、`origin_id` 詐称への同一レート制限。
- 要検証: HB 周期・重みの実機チューニング、Android 前景サービス／Doze 下での HB 維持可否、Wi-Fi Direct GO 再形成の実測所要時間、機種別サーマルスロットリング開始温度。
- Vision 専用の検証（VL 等 AI 機能の本番品質）は本ハッカソンの critical path から除外し、詳細集約は将来の 01_vision_and_scope に送る。
