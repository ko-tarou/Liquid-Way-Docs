# ADR-0003: 動的サーバー選出アルゴリズム

- Status: Proposed
- Date: 2026-05-17
- Deciders: ko-tarou, Mako（参加意思確認中）

---

## Context

LiqMesh は「安定電源を確保した端末が動的に LFM サーバー役に昇格し、悪化したら次点へ無停止引き継ぎ」する（liqmesh.md §4.2、議事録 §9.2）。不安定な災害下メッシュで、以下を満たす leader election を定義します。

| # | 要件 |
|---|---|
| E1 | 充電中／大容量電池／高スペック端末を優先してサーバー化 |
| E2 | 周期ハートビートで生存監視 |
| E3 | サーバー故障時に次点へフェイルオーバー |
| E4 | メッシュ分断時の split-brain と、再結合時のマージ方針 |
| E5 | ADR-0002 の Wi-Fi Direct GO（Group Owner）に選出結果をマッピングできる |

古典的 leader election（Bully / Raft）は「全ノード均質・到達安定」を暗黙前提にしますが、LiqMesh は**電源状態という外部属性で優先順位が決まる**点と**頻繁な分断**が前提な点が異なります。

---

## Decision

**「重み付きサーバー適性スコア + 周期ハートビート + 分断許容（split-brain を許し再結合時にマージ）」を採用する。** Raft のような厳密な過半数合意は採らない（分断が常態で過半数が成立しないため）。

### スコア式

各端末 i は周期的に自スコア S_i をブロードキャストする（液mesh.md §4.2-1 のブロードキャストに対応）。

```
S_i = w_p · P_i        # 電源: AC給電=1.0, モバイルバッテリ=0.6, バッテリ単独=0.0
    + w_b · B_i        # 電池残量 0.0–1.0 (残量%/100)
    + w_c · C_i        # 計算能力 0.0–1.0 (NPU有=1.0, 高CPU=0.6, 低=0.3)
    + w_s · St_i       # 安定度 0.0–1.0 (直近Tでの離脱回数の逆指標)
    - w_l · L_i        # 負荷ペナルティ 0.0–1.0 (現在の推論キュー長/上限)
```

初期重み（要実機チューニング、推測値と明記）: `w_p=0.40, w_b=0.20, w_c=0.25, w_s=0.10, w_l=0.05`。電源を最重要に置くのは liqmesh.md §4.2「安定電源を確保した端末」が一次基準だから。同点時は端末 ID 辞書順で決定的にタイブレーク（再現性のため）。

### 選出・再選出のトリガ

| トリガ | 条件 | 挙動 |
|---|---|---|
| 初期選出 | グループ形成直後、ハートビート 1 周期収集後 | 最大 S_i の端末を Leader=LFM サーバー、ADR-0002 の Wi-Fi Direct GO に固定 |
| ハートビート喪失 | Leader から 3 周期（既定 3×2s=6s、要調整）応答なし | 残存ノードで次点（2 番目に高い S_i）へフェイルオーバー |
| 自発降格 | Leader の S_i が 2 番手より閾値 Δ=0.15 下回り T_hyst=15s 継続 | ヒステリシス付きで次点へ委譲（フラッピング防止） |
| 過負荷 | L_i が上限到達かつ次点 S が現 Leader を上回る | 委譲（ADR-0005 のキュー溢れと連動） |

ハートビート間隔は既定 2s（推測初期値、災害下の電力と検出遅延のトレードオフで要実測調整）。

### 分断（split-brain）と再結合

- **分断は許容する**: メッシュが A/B に割れたら各部分が独立に Leader を選び、各々ローカルに LFM サーバーを持つ（可用性優先 = AP 型）。これは ADR-0004 の「分断中も append し続ける」整合性モデルと整合。
- **再結合時のマージ**: 二つの Leader が再会したら、(1) スコアの高い方を新 Leader に確定、(2) データは ADR-0004 の CRDT マージで統合（どちらの履歴も失わない）、(3) 旧 Leader はクライアントに降格しキューを新 Leader へ転送。
- **エポック番号**: 各 Leader 任期に単調増加エポックを付与し、再結合時に古いエポック由来の制御メッセージを破棄して指揮系統の混線を防ぐ。

## Alternatives Considered

| 案 | 長所 | 短所 | Android 制約 | 却下理由 |
|---|---|---|---|---|
| **重み付きスコア + HB + 分断許容（採用）** | 電源属性を直接反映。分断常態に強い。GO へ素直にマッピング | 厳密合意なし＝一時的多重 Leader を許容（設計上の選択） | バックグラウンド制約下で HB 周期を詰めにくい（doze）。前景サービス前提 | — |
| Bully アルゴリズム | 実装単純、最大 ID が必ず勝つ | ID＝適性ではない（電源無視）。選出時のメッセージ嵐。分断耐性なし | 同上 | E1（電源優先）を表現できない。スコアの方が要件に直結 |
| Raft-lite（過半数合意） | 強い一貫性、Leader 一意保証 | **分断時に過半数が成立せず全停止**しうる。災害下で致命的 | HB を詰めると電力消費大 | E4（分断常態で可用性優先）と根本的に不一致 |
| 固定 Leader（Ryzen AI PC 固定） | 実装ゼロ、デモ安定 | 端末メッシュとして成立しない（LiqMesh の本質を失う） | — | 本番 Vision 不適。ただし 12h MVP のデモ縮退としては併用（議事録 §11） |

## Consequences

### 正の帰結

- 電源・スペックという「サーバーに向くか」の本質属性で選出でき、liqmesh.md §4.2 の意図に忠実。
- 分断を障害でなく通常状態として扱うため、災害下の頻繁な切断で停止しない（可用性優先）。
- ADR-0002 の GO とエポックの対応で、転送層と制御層の責務境界が明確。

### 負の帰結・受容するトレードオフ

- **一時的に複数 Leader が並存**しうる（split-brain 許容の代償）。データ衝突は ADR-0004 の CRDT に委ねる前提で受容。
- スコア重みとハートビート周期は**実機チューニング必須**（現値は推測初期値）。電力と検出遅延はトレードオフ。
- フラッピング対策（ヒステリシス／エポック）を入れる分、制御パスの状態数が増える。

### フォローアップ

- ADR-0004: 再結合マージで失わないための CRDT 型定義。
- ADR-0005: Leader 委譲時の優先度キュー引き継ぎ手順。
- 要検証: HB 周期・重みの実機チューニング、Android 前景サービス／Doze 下での HB 維持可否。
