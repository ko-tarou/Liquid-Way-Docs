# LiqMesh Idea-Aligned Distributed Systems ADR

Status: Proposal

Idea Source Date: 2026-05-12

Updated: 2026-05-22

このファイルは、`docs/ideas/liqmesh.md` の初期構想を分散システム ADR として読みやすく整理するための README である。現行実装や後続のスコープ縮小版ではなく、もともとの idea 側にある「災害時 P2P メッシュ × 動的 LFM サーバー」を正面に置く。

扱う対象は、端末間メッシュ、動的 LFM サーバー昇格、オフライン同期、情報統合、優先度判定、クラウド非依存の運用判断である。UI の細部、提出文面、個別実装タスクはここでは扱わない。

## Context

LiqMesh は、災害時に基地局や固定回線が使えない状況でも、被災者のスマートフォン同士が P2P メッシュを組み、端末だけで被害情報の収集・統合・配信を行うアプリである。

メッシュ内で安定電源や十分な計算資源を持つ端末が動的に「LFM サーバー」へ昇格し、周囲の端末から集まるテキスト、写真、音声などの報告をローカル LFM で処理する。クラウドに個人情報を集約せず、通信断絶下でも災害現場の情報共有を継続することが設計の中心である。

## Core Requirements

| 要件 | 内容 |
|---|---|
| 完全オフライン | インターネットやクラウド API に依存しない |
| P2P メッシュ | Wi-Fi Direct / BLE / 共有 AP などで端末同士が自律接続する |
| 動的 LFM サーバー | 電源・電池残量・性能スコアによりサーバー役を選ぶ |
| 多端末協調 | 単機の防災ガイダンスではなく、被災者間の情報共有を成立させる |
| ローカル AI | 写真キャプション、重複統合、矛盾整理、クエリ応答、優先度判定を端末側で行う |
| データ主権 | 位置、容態、氏名などの機微情報をクラウドへ送らない |

## 技術

分散システム側で使う技術は以下に集約する。Android UI、提出用資料、モデル実験環境など、分散処理の成立に直接関わらない技術はここでは扱わない。

| 領域 | 技術 | 分散システム上の役割 |
|---|---|---|
| 近距離通信 | Wi-Fi Direct / BLE / 共有 AP | 端末発見、近傍接続、メッシュ参加 |
| ネットワークトポロジ | P2P メッシュ | 基地局・クラウドなしで端末間に通信経路を作る |
| ルーティング | ホップ転送 | 直接接続できない端末へ報告を中継する |
| リーダー選出 | 動的 LFM サーバー昇格 | 電源・電池残量・性能スコアで推論担当端末を決める |
| サーバー役実行基盤 | Go サーバーまたは端末内軽量ランタイム | 昇格端末で推論リクエストを受け付ける |
| ローカル推論 | LFM2.5 系 Text / VL | 報告の統合、矛盾整理、クエリ応答、優先度判定をメッシュ内で処理する |
| 永続化 | 端末内 DB | 切断中の報告蓄積、再接続時の差分同期、重複排除 |
| 同期方式 | メッセージ ID + 差分交換 | at-least-once な共有を前提に、受信側で冪等化する |
| プライバシー境界 | ローカル処理 / メッシュ内共有 | 位置・容態・写真などの機微情報をクラウドへ出さない |

## Decisions

### 1. P2P メッシュを中核アーキテクチャにする

LiqMesh の存在意義は、災害時に通信インフラが崩壊しても、端末同士だけで情報流通を継続できる点にある。そのため、基本構成は中央クラウドや固定サーバーではなく P2P メッシュとする。

- 端末は Wi-Fi Direct / BLE / 共有 AP などで近傍端末と接続する。
- メッセージは直接接続だけでなく、必要に応じてホップ転送する。
- 通信インフラが復旧していない状態を通常ケースとして扱う。
- クラウド同期は中核要件ではなく、復旧後の補助機能に留める。

この判断により、LiqMesh は「既存クラウド型防災アプリのオフライン版」ではなく、インフラ不在時の多端末協調システムとして定義される。一方で、端末発見、ルーティング、重複リレー制御、接続維持は主要な技術リスクになる。

### 2. LFM サーバー役は動的に昇格させる

メッシュ内で最もサーバー適性が高い端末を、動的に LFM サーバー役へ昇格させる。

- 各端末は電源接続状態、電池残量、CPU / NPU 性能などを共有する。
- それらをもとにサーバー適性スコアを計算する。
- 最も適性が高い端末が LFM ランタイムを起動し、推論リクエストを受ける。
- 状態悪化や離脱時には次点端末へ役割を引き継ぐ。

この判断により、電力や計算資源を持つ端末に重い処理を寄せられる。災害現場では全端末が同じ能力や電源状態ではないため、役割分担をシステム側で吸収する。一方で、二重昇格、世代管理、引き継ぎ時の履歴整合性が設計課題になる。

### 3. LFM は情報整理の中核として扱う

LFM は単なるチャット補助ではなく、被災情報を実用可能な形に変換する中核コンポーネントとする。

対象機能は以下。

- 写真から状況キャプションを生成する。
- 複数の短文報告を重複統合する。
- 矛盾する報告を片方に潰さず併記する。
- 「水が足りない避難所は？」のような自然言語クエリに答える。
- 位置や種別で報告を粗くグルーピングする。
- 救援優先度を `critical` / `high` / `medium` / `low` などに分類する。

この判断により、LiqMesh は「メッセージを運ぶだけ」のアプリではなく、通信断絶下で災害情報を整理するローカル AI システムになる。一方で、モデル品質、推論負荷、電力消費、誤判定時の表示責任を明確に扱う必要がある。

### 4. 個人情報はクラウドに送らず、ローカル協調で処理する

位置、容態、氏名、写真などの機微情報は、原則としてクラウドへ送らない。処理は端末内またはメッシュ内の LFM サーバー端末で完結させる。

- クラウド LLM / SaaS を通常経路にしない。
- メッシュ内で必要最小限の報告だけを共有する。
- 復旧後の外部送信が必要な場合も、差分同期や匿名化を別途判断する。

この判断により、災害時のプライバシー懸念とクラウド到達不可問題を同時に避ける。一方で、クラウド側の大規模モデルや集中 DB に頼れないため、端末側のモデル性能と同期設計が品質上限を決める。

### 5. オフライン蓄積と差分同期を前提にする

災害時は接続が断続的になるため、各端末は報告をローカルに蓄積し、再接続時に差分同期する。

- 投稿はまず端末内 DB に保存する。
- 各報告には一意なメッセージ ID を持たせる。
- 再接続時は未共有の差分を交換する。
- 受信側はメッセージ ID で重複排除する。
- 編集・削除・厳密な因果順序よりも、追記型の情報共有を優先する。

この判断により、一時的な孤立や移動をまたいでも情報を失いにくくなる。一方で、完全な全順序、強整合、複雑な競合解決は対象外にするか、後続 ADR で別途扱う。

### 6. デモ構成では共有 AP や Ryzen AI PC を利用できる

本来の構想は端末同士の自律メッシュだが、デモでは Wi-Fi Direct / BLE の不確実性を下げるため、共有 AP や Ryzen AI PC を基地局兼 LFM サーバーとして使う構成を許容する。

- 観客スマートフォンは QR コードなどでクライアントへ参加する。
- 共有 AP 内で報告を集める。
- Ryzen AI PC または安定電源端末が LFM 処理を担う。
- 会場スクリーンに災害マップや W&B ダッシュボードを表示する。

これは本番構想の否定ではなく、ハッカソンデモの成立性を上げるための縮約である。実運用版では端末間メッシュと動的昇格へ戻す。

## Alternatives Considered

- クラウド集約型: 通常時は実装しやすいが、通信断絶と個人情報集約の問題を解けない。
- 単機オフライン防災ガイダンス: 端末単体では動くが、被災者間の情報共有や重複統合が成立しない。
- 固定 LFM サーバー: 設計は単純だが、災害現場でその端末が使える保証がない。
- 手動サーバー選択のみ: MVP では有効だが、idea 側の「安定電源端末が自然に中核化する」構想からは弱くなる。
- リアルタイム音声会議: 通信・電力負荷が大きく、災害情報整理という主目的から外れる。
- 教育・エンタメ・翻訳用途: LFM 活用例としては成立するが、LiqMesh の災害ドメインとは合わない。

## Open Questions

- Wi-Fi Direct と BLE のどちらを主経路にするか、または共有 AP を前提に含めるか。
- 動的サーバー昇格のスコア式をどう定義するか。
- 昇格端末の離脱時に、推論履歴や未処理キューをどこまで引き継ぐか。
- 複数 LFM サーバーが同時に存在した場合の責務分担をどうするか。
- 写真、音声、位置情報をどの粒度で共有すれば、プライバシーと有用性のバランスが取れるか。
- Function Calling を救援アクション提案に使えるか。
- W&B エッジ計測がオフライン前提のデモに適合するか。
