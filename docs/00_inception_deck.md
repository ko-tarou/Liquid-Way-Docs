## 1行サマリ / エレベーターピッチ

災害時、インターネットが途絶しても端末同士が P2P で直接つながるチャット型 Android アプリ。誰かが端末を「サーバーモード」に切り替えると、その端末上で動く LFM が流れてくる情報を要約・整理して周囲の端末へ配信する。

## なぜやるか

- 災害時に通信インフラが途絶しても、LFM をローカルで動かして情報整理を続けられる。
- Hack the Liquid WAY 公式テーマ「パラメータあたりの性能と計算メモリの効率」に直結（小型 LFM をオフライン端末上で実用化する）。

## やること / やらないこと

**やること**
- P2P によるオフラインチャット
- サーバーモードに切り替えた端末上での LFM 要約・配信

**やらないこと（Out of Scope）**
- iOS 対応
- React / PWA / Hybrid（Web 系 UI）
- 動的なサーバー選出アルゴリズム（人間が手動で決める）
- CRDT 等の重い競合解決（メッセージID重複排除で代替）
- 優先度ルーティングの詳細設計（機能の存在のみ宣言、設計は後日）

## 技術スタック

- プラットフォーム: Android のみ
- 言語/UI: Native Kotlin + Jetpack Compose
- LLM: LFM（LFM2.5 系）を **transformers で「直」実行**（llama.cpp は使わない）
- 端末間通信: P2P（Wi-Fi Direct ベース。詳細は後日）
- ローカル保存: 端末内DB（Room 想定）。再接続時に共有し、メッセージID で重複排除（CRDT 不採用）

> 注: 技術選定の根拠はここに集約。個別 ADR は作らない。

## サーバー化の考え方

- ユーザーが設定画面で「サーバーモード ON」にすると、その端末がサーバー化し LFM を起動する。
- 誰がサーバーになるかは**人間が決める**。動的選出はしない。

## 機能要件

- P2P チャットの送受信
- オフライン時はローカルキャッシュ → 再接続で同期
- サーバーモードのトグル
- サーバー端末上の LFM による情報の要約・配信
- 優先度の高い情報を優先表示（※詳細設計は後日。ここでは存在のみ宣言）
- 写真添付（VL = 画像理解は将来対応）

## 非機能要件

- 完全オフライン動作（インターネット不要）
- 省電力を意識した実装
- サーバー端末のメモリ ~1GB 級
  - experiment 001 実測: LFM2.5-350M を素 transformers で実行 → RSS 約1GB / 7〜13 tok/s
- レイテンシは体感許容範囲に収まればよい（厳密な SLA は設けない）

## 主要リスク（Top 5）

1. P2P の多端末スケールが未検証（数端末を超えた挙動が不明）。
2. スマホ単体での transformers 実行は非現実的 → MVP のサーバー役は PC 前提。
3. 本番 12 時間で作り切れる範囲の絞り込みが甘いと未完成リスク。
4. Mako（開発体制）が未確定で工数見積りが不安定。
5. transformers 直実行のメモリ・速度が想定環境で再現するか未検証。

## 前提・未決（要確認）

- **【要確認の前提】MVP のサーバー役は、提供される Ryzen AI PC。Android はそのクライアントとして動く。** スマホ自身の「サーバーモード ON」は本番 Vision としての概念であり、MVP では PC がサーバーを担う。
- **【要確認】Go バックエンドは旧構想。** 現状は transformers（Python）でのサーバー実装を想定するが未確定。レビューで覆る可能性あり。
