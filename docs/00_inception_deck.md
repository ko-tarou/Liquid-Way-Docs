## 1行サマリ / エレベーターピッチ

災害時、インターネットが途絶しても端末同士が P2P で直接つながるチャット型 Android アプリ。誰かが端末を「サーバーモード」に切り替えると、その端末上で動く LFM が流れてくる情報を要約・整理して周囲の端末へ配信する。

## なぜやるか

- 災害時に通信インフラが途絶しても、LFM をローカルで動かして情報整理を続けられる。
- Hack the Liquid WAY 公式テーマ「パラメータあたりの性能と計算メモリの効率」に直結（小型 LFM をオフライン端末上で実用化する）。

## やること / やらないこと

**やること**
- P2P によるオフラインチャット
- サーバーモードに切り替えた端末上での LFM 要約・配信
- 通信が逼迫した際、チャットを優先的に伝送する優先度ルーティング（実施確定・詳細設計は後日）

**やらないこと（Out of Scope）**
- iOS 対応
- React / PWA / Hybrid（Web 系 UI）
- 動的なサーバー選出アルゴリズム（人間が手動で決める）
- CRDT 等の重い競合解決（メッセージID重複排除で代替）
- インターネット／基地局への依存（**完全オフライン動作を大前提**とし、外部回線は一切利用しない）

## 技術スタック

- プラットフォーム: Android のみ
- 言語/UI: Native Kotlin + Jetpack Compose
- LLM: LFM（LFM2.5 系）を **Android 端末上で LEAP SDK（Liquid 公式・Kotlin）でオンデバイス実行**。MVP・本番とも LEAP に一本化。`transformers` は実験・品質確認専用で**製品スタックから除外**。
- 端末間通信: P2P（Wi-Fi Direct ベース）。**L4 は TCP では不足の懸念があり、UDP もしくは専用プロトコルを要検討（未決）**。
- ローカル保存: 端末内DB（Room 想定）。再接続時に共有し、メッセージID で重複排除（CRDT 不採用）

> 注: 技術選定の根拠はここに集約。個別 ADR は作らない。

## サーバー化の考え方

- ユーザーが設定画面で「サーバーモード ON」にすると、その Android 端末が LEAP でローカルに LFM を起動し、サーバー化する。
- 誰がサーバーになるかは人間が設定画面で決める。

## 機能要件

- P2P チャットの送受信
- オフライン時はローカルキャッシュ → 再接続で同期
- サーバーモードのトグル
- サーバー端末上の LFM による情報の要約・配信
- 優先度の高い情報を優先表示（※詳細設計は後日。ここでは存在のみ宣言）
- 写真添付は通信負荷が大きいため**重大な非常時のみ許可**、通常時は制限（VL = 画像理解は将来対応）

## 非機能要件

- 完全オフライン動作（インターネット不要）
- 低消費電力を意識した実装
- サーバー役端末のメモリ管理 ~1GB 級（experiment 001 実測: LFM2.5-350M を素 transformers で実行 → RSS 約1GB / 7〜13 tok/s を根拠）
- レイテンシは体感許容範囲に収まればよい（厳密な SLA は設けない）

## 主要リスク（Top 5）

1. P2P の多端末スケールが未検証（数端末を超えた挙動が不明）。
2. LEAP の量子化による LFM 出力品質の低下度が未計測。
3. 本番の実作業時間で作り切れる範囲の絞り込みが甘いと未完成リスク。
4. 開発体制は当面ソロ前提で進める（Mako の担当は後日確定）ため工数が逼迫しうる。
5. 優先度ルーティングの詳細設計が後日のため、当日に設計負債が顕在化しうる。

## 前提・未決（要確認）

- **【未決】LEAP 量子化による品質低下度は未計測 → 実機で計測して再判断する。**
- **【前提】開発体制は当面ソロ前提で進める。** Mako の担当範囲は後日確定。
