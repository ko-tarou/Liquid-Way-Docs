## 5. LFM モデル群（調査結果）

| 観点 | 当初仮説 | 補正後 |

## 9. アイデア深掘り: A' → 「LiqMesh」への進化

午後の議論で、最有力案だった A'（災害時オフライン × スマホ多者通信）を一段抽象化し、**正式名「LiqMesh」** として再定義しました。コアコンセプトは「**P2P メッシュ + 動的 LFM サーバー**」です。

### 9.1 コアコンセプト

- 災害発生時、被災者のスマートフォン同士が **P2P でメッシュネットワーク** を組む
- メッシュ内で **安定電源を確保した端末**（例: モバイルバッテリー、被災を免れた家屋のコンセント、提供 Ryzen AI PC）が **動的に「LFM サーバー」役** に昇格
- 周囲のクライアント端末から被害状況（写真・テキスト・音声）を収集
- サーバー側で LFM が**重複統合・矛盾解消・優先度判定・地理クラスタリング**を行い、被災マップを **完全オフラインで** 生成・配信

### 9.2 機能スペックの Tier 分け

議論の中で、「あれもこれも」を避けるため、各機能を 3 段階に明示的に分類しました。

| 区分 | 機能 | 備考 |
|---|---|---|
| ✅ 必須 | P2P メッシュ通信（端末間ホップ） | LiqMesh の存在意義そのもの |
| ✅ 必須 | 動的 LFM サーバー昇格 | 安定電源端末を自動選出 |
| ✅ 必須 | 写真 → 状況キャプション（VL） | LFM2.5-VL を使う必然性 |
| ✅ 必須 | テキスト重複統合・矛盾解消 | LFM2.5 テキスト |
| ✅ 必須 | 自然言語クエリ応答 | 「水が足りない避難所は？」等 |
| ✅ 必須 | 優先度判定 AI | **6 つ目のキラー機能**として追加 |
| ⭕ 強化 | Function Calling による救援アクション提案 | LFM 公式 README で未確認、要検証 |
| ⭕ 強化 | 自動グルーピング（地理 × 種別） | 現実的には粗いクラスタリングで十分 |
| ⭕ 強化 | オフライン蓄積 / 接続復活時の自動同期 | クラウドリレーが復活した瞬間の挙動 |
| ❌ 削除 | リアルタイム音声会議 | スコープ膨張・電力負荷大 |
| ❌ 削除 | 教育コンテンツ配信 | 災害時のユースケースに不一致 |
| ❌ 削除 | エンタメ / 翻訳機能 | テーマと整合せず |

### 9.3 レイヤード・アーキテクチャ

3 層構造で整理しました。

```
┌─────────────────────────────────────────────┐
│  Layer 3: UI / UX                          │
│  - Android Native（Kotlin / Jetpack）       │
│  - 災害マップ表示、報告投稿、検索クエリ        │
└─────────────────────────────────────────────┘
                  ▲
                  │ HTTP / WebSocket（LAN 内）
                  ▼
┌─────────────────────────────────────────────┐
│  Layer 2: LFM Inference Server（動的昇格）   │
│  - Go サーバー（軽量・並行性）                │
│  - LFM 直ネイティブ実行（VL + Text）          │
│  - 重複統合 / 優先度判定 / クエリ応答          │
└─────────────────────────────────────────────┘
                  ▲
                  │ Wi-Fi Direct / BLE / LAN
                  ▼
┌─────────────────────────────────────────────┐
│  Layer 1: P2P Mesh Transport               │
│  - 端末発見・ホップ転送                       │
│  - サーバー選出（電源・電池・性能）            │
│  - メッシュ崩壊時のフェイルオーバー            │
└─────────────────────────────────────────────┘
```

### 9.4 「機密性 vs オフライン」軸の競合分析

公式テーマの 6 軸のうち、特に競合が集中する「機密性」と「オフライン」を 2 軸で整理しました。

| 軸 | 機密性のみ重視 | オフラインのみ重視 | **両方必須**（LiqMesh が狙う） |
|---|---|---|---|
| 例 | 社内文書要約 | カーナビ、登山ログ | **災害時被災情報** |
| クラウド代替可？ | △ VPC で代替可 | △ オンデバイス代替可 | **× クラウド到達不可 & 個人情報を晒せない** |
| LFM 必然性 | 弱い | 中 | **強い（唯一解）** |

「両方必須シナリオ」は災害・医療現場・軍事用途など限られており、その中で **観客がデモで体感できる** のは災害領域である、と判断しました。

### 9.5 検討して却下した方向性

| 案 | 却下理由 |
|---|---|
| 教育系（オフライン教材 AI） | 災害との接続が薄く、ストーリーがブレる。テーマ「産業インパクト」との結びつきも弱い |
| 漫画翻訳 | **前回（Hack #03）受賞作の系譜（VLM 系）と被る**。新規性が出しにくい |
| 緊急時セルラー（衛星 / 既存 MNO 提供 Wi-Fi スポット） | 既に総務省や MNO が整備中。**LiqMesh の差別化は「インフラ完全ゼロ・端末だけで成立」する点** にある |

### 9.6 優先度判定 AI（6 つ目のキラー機能）

当初 5 機能（VL キャプション / 重複統合 / クエリ応答 / Function Calling / グルーピング）で確定としていたところ、議論の中で **「優先度判定」** を 6 つ目として追加しました。

- 例: 「重傷者の SOS」と「水が欲しい」が同時に来た場合、前者を最上位に押し上げる
- 災害現場のトリアージ思想と合致
- LFM2.5 のテキスト推論能力で実装可能

### 9.7 オフライン蓄積 / 自動同期の仕様

- 通信完全断絶中はサーバー（昇格端末）内に **時系列ログとして蓄積**
- 上位接続（Starlink / 衛星 / 復旧した MNO）が回復した瞬間に **差分のみクラウドへ同期**
- クラウド側は外部 API（自治体ダッシュボード等）への配信窓口に徹する

### 9.8 地理クラスタリングの現実認識

- 厳密な地図グリッドや POI マッチは MVP では非現実的
- **「避難所 A の周辺 200m」** 程度の粗いクラスタリングで十分
- 端末 GPS の誤差を AI 側で許容する設計（「だいたい同じ場所」と判定する閾値ロジック）

## 10. 技術選定（本番 Vision）

| レイヤ | 技術 | 採用理由 |
|---|---|---|
| Android クライアント | **Native Kotlin（Jetpack Compose）** | 電力効率が最重要。React Native / Flutter は劣後 |
| サーバー | **Go** | 軽量・並行性・クロスコンパイル容易、Ryzen AI PC との親和性も良好 |
| LFM ランタイム | **LFM 直ネイティブ実行を優先トライ** | 最適化済みカーネルが使える可能性。だめなら Lemonade SDK / FastFlowLM にフォールバック |
| iOS / PC クライアント | Stretch goal | Android 一本で MVP を仕上げる |

## 11. スコープ分離: 本番 Vision vs Hackathon 12 時間 MVP

「LiqMesh は本来 1 ヶ月案件」のスコープであることを認識し、**12 時間で組める範囲** に明確に絞ります。

| 項目 | 本番 Vision | Hackathon 12 時間 MVP |
|---|---|---|
| クライアント | Native Kotlin + Jetpack | **同左 or 簡易 PWA**（時間で判断） |
| サーバー | Go + LFM 直ネイティブ | **同左 or Python + Lemonade SDK**（時間で判断） |
| P2P 通信 | フル実装（ホップ転送 + 選出） | **Wi-Fi AP（Ryzen AI PC）を中心とした星型** で代用 |
| 機能数 | 6 機能 | **3〜4 機能に絞る**（VL キャプション / 重複統合 / クエリ応答 + 1） |
| Function Calling | 強化機能 | スコープ外（時間が余れば挑戦） |
