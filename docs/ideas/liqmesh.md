# LiqMesh — 災害時 P2P メッシュ × 動的 LFM サーバー

> Status: Proposal (2026-05-12)
> Owner: ko-tarou / Mako（参加意思確認中）

---

## 1. 1 行サマリ

災害時にスマホ同士が P2P でメッシュネットワークを組み、安定電源を確保した端末が動的に「LFM サーバー」となって、被害情報の収集・統合・配信を **完全オフライン** で行うアプリです。

---

## 2. 解決する課題

| # | 課題 | 現状 |
|---|---|---|
| 1 | 災害時、通信インフラ（基地局・固定回線）が崩壊する | 既存の防災アプリはほぼクラウド前提 |
| 2 | クラウド到達不可な状況下では既存 AI / SaaS が機能停止する | 被災者は孤立したまま情報が分散・重複・矛盾する |
| 3 | 避難所での被災者間の情報共有手段が貧弱 | 紙の張り紙、口頭、限定的な防災無線に依存 |
| 4 | 個人情報（位置・容態・氏名）をクラウドに上げる懸念 | プライバシー軽視の集約は社会的に許容されにくい |

LiqMesh はこの 4 つを **「端末同士の協調 × ローカル LFM」だけで** 同時に解きます。

---

## 3. なぜ LFM でしか成立しないか

クラウド到達不可・電力制約・端末プラットフォーム多様性という条件下で、以下 6 機能を全てローカルで成立させるには **小型・高速・マルチモーダルな LFM が唯一解** です。

| # | 機能 | クラウド LLM では不可能な理由 | LFM で可能な理由 |
|---|---|---|---|
| 1 | 写真 → 状況キャプション（VL） | 通信切断中はクラウド API 到達不可 | LFM2.5-VL-450M / 1.6B が **512×512 ネイティブ**、スマホで動作 |
| 2 | テキスト重複統合・矛盾解消 | 大量の短文を都度クラウド送信は非現実的 | LFM2.5-1.2B-JP が **70〜82 t/s** で端末動作 |
| 3 | 自然言語クエリ応答 | レイテンシと帯域が成立しない | LAN 内 LFM サーバーでミリ秒応答 |
| 4 | Function Calling による救援アクション提案 | クラウド前提のツール群とは別系統 | LFM の構造化出力で **ローカル API** を駆動 |
| 5 | 自動グルーピング（地理 × 種別） | 都度クラウド推論はコスト・電力に響く | エッジ推論で電力 1/N |
| 6 | 優先度判定（トリアージ） | 通信断絶下では応答不能 | 推論特化 1.2B-Thinking が NPU で 52 t/s |

## 4. アーキテクチャ

### 4.1 レイヤード構造

```
┌───────────────────────────────────────────────────────┐
│  Layer 3: UI / UX                                     │
│  ─────────────────────────────────────────────────    │
│  - Android Native（Kotlin / Jetpack Compose）         │
│  - 災害マップ表示 / 報告投稿 / 自然言語クエリ           │
│  - オフライン表示前提、復帰時に差分同期                  │
└───────────────────────────────────────────────────────┘
                         ▲
                         │ HTTP / WebSocket（LAN 内）
                         ▼
┌───────────────────────────────────────────────────────┐
│  Layer 2: LFM Inference Server（動的昇格）             │
│  ─────────────────────────────────────────────────    │
│  - Go サーバー（軽量・並行・クロスコンパイル）           │
│  - LFM 直ネイティブ実行（VL + Text）                   │
│  - 重複統合 / 優先度判定 / クエリ応答 / Function Call  │
│  - W&B エッジ計測（トークン・レイテンシ・電力）         │
└───────────────────────────────────────────────────────┘
                         ▲
                         │ Wi-Fi Direct / BLE / 共有 AP
                         ▼
┌───────────────────────────────────────────────────────┐
│  Layer 1: P2P Mesh Transport                          │
│  ─────────────────────────────────────────────────    │
│  - 端末発見 / ホップ転送 / メッセージリレー              │
│  - 動的サーバー選出（電源・電池残量・性能スコア）         │
│  - メッシュ崩壊時のフェイルオーバー                     │
└───────────────────────────────────────────────────────┘
```

### 4.2 動的サーバー昇格ロジック

1. 各端末は定期的に **電源接続状態 / 電池残量 / CPU・NPU スペック** をブロードキャストします。
2. メッシュ内で最も「サーバー適性スコア」が高い端末が **LFM サーバー役** に昇格します。
3. 昇格端末は LFM ランタイムを起動し、他端末からの推論リクエストを受け付けます。
4. 昇格端末の状態が悪化した場合、次点端末に **無停止で引き継ぎ** ます。

| ✅ 必須 | P2P メッシュ通信 | LiqMesh の存在意義 |

| ✅ 必須 | 写真 → 状況キャプション（VL） | LFM2.5-VL の出番 |
| ✅ 必須 | テキスト重複統合・矛盾解消 | LFM2.5 テキスト |
| ✅ 必須 | 自然言語クエリ応答 | 「水が足りない避難所は？」 |
| ✅ 必須 | 優先度判定 AI（トリアージ） | 6 つ目のキラー機能 |

## 6. AI 機能詳細（6 つ）

### 6.1 写真 → 状況キャプション（VL）

- モデル: **LFM2.5-VL-450M または 1.6B**
- 入力: 被災現場の写真（瓦礫、浸水、火災、負傷者など）
- 出力: 「2 階建て住宅が半壊。電柱倒壊あり。負傷者は確認できない。」
- 用途: 視覚情報を構造化テキストへ変換し、後段の統合・優先度判定に流す

### 6.2 テキスト重複統合・矛盾解消

- モデル: **LFM2.5-1.2B-JP**
- 入力: 複数端末からの短文報告群
- 出力: 1 つの統合レポート（矛盾は「報告 A: ◯◯ / 報告 B: ××」と併記）
- 用途: 「水が足りない」が 30 件来ても 1 件に集約。位置・時刻でグルーピング

### 6.3 自然言語クエリ応答

- モデル: **LFM2.5-1.2B-JP** または **1.2B-Thinking**
- 入力: 「水が足りていない避難所は？」
- 出力: 「現在 3 ヶ所。避難所 A（深刻）、避難所 B（中）、避難所 C（軽微）」
- 用途: 救援者・被災者が自由文で災害状況を問い合わせる

### 6.4 Function Calling による救援アクション提案

- モデル: **LFM2.5** ※ 対応状況を要確認
- 入力: 被害状況の統合レポート
- 出力: 構造化アクション（`dispatch_water(避難所A, 量=100L, 優先度=高)`）
- 用途: ローカル API（避難所ダッシュボード）を直接駆動

### 6.5 自動グルーピング（地理 × 種別）

- モデル: **LFM2.5-1.2B-JP** + GPS 座標
- 入力: 多数の報告 + 端末 GPS
- 出力: 「避難所 A の 200m 圏内」「給水ニーズ」などの粗いクラスタ
- 用途: マップ上に集約ピンを立てる

### 6.6 優先度判定（トリアージ）

- モデル: **LFM2.5-1.2B-Thinking**
- 入力: グルーピング済みの報告群
- 出力: 各報告に `priority: critical / high / medium / low`
- 用途: 「重傷者 SOS」を「水不足」より上に押し上げる。災害現場のトリアージ思想

## 7. 技術スタック

### 7.1 本番 Vision

| レイヤ | 採用 | 理由 |
|---|---|---|
| Android クライアント | **Native Kotlin + Jetpack Compose** | 電力効率最優先。RN / Flutter は劣後 |
| サーバー | **Go** | 軽量・並行性・クロスコンパイル容易 |
| LFM ランタイム | **LFM 直ネイティブ実行** | 最適化済みカーネルを使う |
| iOS / PC | Stretch goal | Android 一本で MVP 完了 |
| 計測 | **W&B エッジ計測** | 必須提出条件 |

### 7.2 Hackathon MVP（12 時間で組む範囲）

最終確定は後日（応募採択後の準備期間で判断）。候補は以下。

| 候補 | 利点 | 欠点 |
|---|---|---|
| Native Kotlin + Go（本番と同じ） | ストーリー一貫 | 12 時間では厳しい |
| **PWA + Python + Lemonade SDK** | OpenAI 互換 API で爆速組立 | 電力訴求が弱まる |
| ハイブリッド（PWA クライアント + Go サーバー） | 双方の利点取り | 統合テストが重い |

→ 応募採択後、Mako さんと相談して最終決定します。

## 8. デモシナリオ

### 8.1 構成

- **Ryzen AI PC = Wi-Fi AP**（提供ハードを基地局兼 LFM サーバーとして運用）
- 観客のスマートフォン = クライアント
- 会場スクリーン = 災害マップのライブ表示 + W&B ダッシュボード

### 8.2 流れ

1. 観客が会場で **QR コードを読み取る** → ブラウザでクライアントが開く（事前インストール不要）
2. 観客が **「災害現場の写真」「テキスト報告」「音声報告」** を投稿
3. Ryzen AI PC 上の LFM が **キャプション → 統合 → 優先度判定** を自動実行
4. 会場スクリーンに **災害マップが自動生成される様子をリアルタイム表示**
5. 同時に **W&B のダッシュボード** で トークン / レイテンシ / 電力を **ライブ計測**
6. 審査員が「水が足りない避難所は？」と自然言語でクエリ → LFM が即応答

| 決定性 & 制御性 | ★★★★ | 優先度判定 / 重複統合の挙動を明示的に制御 |
